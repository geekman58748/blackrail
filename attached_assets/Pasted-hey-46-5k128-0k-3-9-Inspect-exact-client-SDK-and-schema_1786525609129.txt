Yes, we can wire it up. __No, we should not discard the Payments API entirely.__ The clean design is a hybrid with two settlement modes.

__How they work together__

1. __Standard payment path:__ use MagicBlock’s Payments API for ordinary private transfers. It is simpler and already handles transaction construction, gasless behavior, and private transfer infrastructure.

2. __Conditional payment path:__ use your deployed `mirage-vault` program when a session needs custom rules.

3. Store a settlement mode on each session, such as `standard` or `conditional`.

4. The backend routes settlement accordingly:

   - `standard` → existing `settleFacade()` Payments API flow.
   - `conditional` → initialize intent on L1, delegate it, execute `authorize_release` on the ER, commit/undelegate, then call `settle` on L1.

The Payments API remains useful plumbing. Your program becomes the policy engine for cases the API cannot express.

__What ER delegation adds__

The Payments API is like ordering from a fixed menu: transfer this amount, split it, delay it, and use the options MagicBlock exposes.

ER delegation lets you temporarily move __your program-owned settlement state__ to MagicBlock’s fast validator and run __your own deployed instruction__ against it. That means you control rules such as:

- release only after a merchant-defined time;
- require buyer and merchant approval;
- block release while a dispute flag is active;
- calculate a custom merchant/platform/refund split;
- process many state changes quickly before committing one result to L1.

The important distinction is not merely speed or privacy. It is __programmability__: the API executes MagicBlock’s predefined payment behavior; delegation executes your program’s behavior.

__What we can implement next__

The repo already has the Rust SDK, TypeScript SDK, deployed program, and generated IDL. Wiring is feasible, but it should be done as a proper workflow rather than replacing one function:

- add settlement policy fields to sessions;
- add backend helpers for `initializeIntent`, `delegateIntent`, ER `authorizeRelease`, and L1 `settle`;
- route conditional sessions through those helpers;
- preserve the Payments API for standard sessions;
- add retryable workflow states because delegation and commit are multi-transaction operations;
- add integration tests on devnet.

One important limitation: the current program only checks __amount and expiry__. A genuine dispute window, two-party approval, or custom split needs additional state and instructions in `programs/mirage-vault/src/lib.rs`, followed by another program upgrade. So we can connect today’s program first, but we should define the exact merchant rule before calling it a full dispute system.
